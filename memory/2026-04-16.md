## 2026-04-16

- `lib/finance/queries.ts`: budget movement funding summaries must net both the receiving `funding` side and the `givingFunding` side. A shared `getBudgetMovementFundingImpacts()` helper now returns signed per-funding contributions, and both the budget-movements summary and tracker funding follow-up use it.
- `lib/finance/queries.ts`: budget-movement filtering for a selected funding must match either the receiving or giving side, otherwise outbound transfers disappear from the net funding view.
- `lib/finance/queries.ts`: tracker budget summary rows now apply signed movement impacts to `budget`, `amountGivenBudget`, `financeViewBudget`, and the bucket totals so outbound budget movements reduce the originating funding instead of only increasing the receiving side.
- `lib/finance/queries.ts`: tracker budget summary should net movement impacts by project code, using `budgetArea.projectCode` as the source side and `receivingProjectCode` as the destination side. That keeps outbound movements from inflating the originating pillar.
- Validation for this change: `npm test -- --test-name-pattern="getBudgetMovementFundingImpacts"` and `npm run build`.
- `BudgetMovement` tracker rows need source attribution from `givingPillar` when it contains a project-code-like value (for example `L44530001`), while `receivingProjectCode` remains the destination side. Using the wrong source field can zero out every tracker budget because many stored rows keep the same code on both sides.
- Cloud actual deviation calculations must preserve the original month forecast by cloning the seat/month with `forecastIncluded: true` before deriving the comparison snapshot. Reusing the post-actual forecast state can zero out the value that the UI should compare against the entered actual.
- Cloud comparison reads should treat a stored `usedForecastAmount` of `0` as stale for actuals-month comparisons and recompute the preserved forecast instead. This avoids old rows continuing to show zero forecast in the spent-to-date tooltip after the fix.
- In the "Review forecast conversion to actual" dialog, open seats should seed the override actual input with `0` in the preview state. This is a UI default only; the conversion logic still uses the preview amount values when applying the bulk update.
- Tracker seats now carry `originalStartDate` on the `TrackerSeat` row. Roster derivation and manual seat creation set it once on first write, and later profile updates preserve the existing value even if `startDate` changes. The migration backfills existing rows from their current `startDate`.
- The tracker seat detail dialog now shows both the preserved `originalStartDate` and the current `startDate`, which makes later start-date edits visible without losing the historical first-start value.
- The tracker detail snapshot now returns `originalStartDate` explicitly so the dialog does not depend on implied spread behavior.
- Tracker rows on the main page now compare year-end spent against an `originalTotalForecast` computed from the preserved original start date, so later start-date edits do not shrink the baseline budget used in the deviation label.
- The tracker page baseline should follow the base forecast snapshot (`ignoreForecastOverrides: true`), exposed as `baseTotalForecast`, rather than trying to reconstruct the original number only from dates. That matches the actuals-page forecast history behavior and avoids showing `0` when the seat itself never changed dates.
- The tracker row label now reads `vs full-year budget` to match the annualized baseline math (`baseTotalForecast - yearEndSpent`) instead of implying a historical original-start-date comparison.
- The tracker full-year comparison should use the sum of `baseMonthlyForecast`, not `totalForecast` or a start-date-derived forecast. For cloud rows this is the annualized 12-month budget (`12 × 675,000 = 8,100,000`) and the comparison label should show the remaining budget after subtracting year-end spent.
- The tracker workspace now exposes `annualizedFullYearBudget` directly from the query layer and the table uses that field first. This avoids comparing year-end spend against a post-actual forecast or a forecast that has already had inactive months clipped out.
- `annualizedFullYearBudget` must be the sum of the base monthly forecast values, not `totalForecast`. That is what produces the expected `8,100,000` cloud budget from `12 × 675,000` and yields the correct `221,383` comparison against year-end spent.
- The tracker row render should prefer `baseMonthlyForecast.reduce(...)` over the cached `annualizedFullYearBudget` field. On some rows the cached annualized field can still come through as `0`, and the base monthly array is the reliable source for the `8,100,000 - 7,878,617 = 221,383` comparison.
- The tracker seat comparison line ultimately needs the sum of `seat.months[].comparisonForecastAmount`, because that is the source that already carries the annualized monthly budget for cloud rows. The cached annualized fields and `baseMonthlyForecast` can both be stale or zero on the cloud seat row, which is why the visible diff must be derived from the per-month comparison forecast instead.
- The final tracker full-year budget rule is: annualize the seat's current remaining forecast across the number of forecast months present on the row, then subtract year-end spent. For the cloud seat this is `remainingForecast 6,075,000 / 9 * 12 = 8,100,000`, which yields the expected `221,383` deviation against `7,878,617` year-end spent.
